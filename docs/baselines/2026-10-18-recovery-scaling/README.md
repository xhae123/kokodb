# Incremental WAL Recovery Validation

A small WAL could trigger several gigabytes of temporary allocation during open. The previous recovery path constructed an immutable candidate table and rebuilt its complete primary-key set after every splice. Appending N single-row records repeatedly checked the growing prefix, causing near-quadratic allocation in the measured fixture.

Recovery now maintains a private mutable row list and key set for each replayed table, validates changed keys incrementally, and freezes immutable tables only after the entire valid WAL prefix succeeds. A failure invalidates the builder and aborts open. This changes recovery working state, not live transaction isolation, WAL format or durable-write acknowledgment.

## Identical WAL inputs, three fresh JVMs per runtime

`RecoveryProbe.java` creates an empty snapshot, a schema frame and one INSERT frame per row using the actual version-2 codec. Construction is outside the timed interval. Each JVM warms with three 1,000-row opens, then measures three opens each at 4,000 and 16,000 rows. Every returned ID/value is checked without assuming SQL result order. Timed intervals cover `Database.open`; validation and close are outside them.

| Rows | WAL bytes | Before median open | After median open | Before allocated bytes | After allocated bytes |
|---|---:|---:|---:|---:|---:|
| 4,000 | 403,013 | 156.684 ms | 38.578 ms | 402,096,944 | 16,987,344 |
| 16,000 | 1,621,013 | 1,772.103 ms | 92.253 ms | 6,216,102,184 | 58,765,520 |

- Each cell is the median of nine observations across three JVMs. Raw CSV files and min/max values are included. At 16,000 rows, open ranges were 1,724.681–2,217.420 ms before and 87.656–103.516 ms after.
- Allocated bytes are cumulative allocations on the opening thread, not retained heap or RSS. The 16,000-row fixture reduced this measure by about 99.1% and open time by about 94.8%.
- Whole-process peak RSS medians were 133,300,224 and 103,006,208 bytes. These include fixture construction, warmup and validation, and cannot be attributed solely to the retained database.
- The working directory, JVM and filesystem caches are warm during measured opens. These are not fresh-JVM startup or cold-device latency measurements. File creation does not model separately forced writer acknowledgments and is not a write-throughput benchmark.
- The comparison is against the prior KoKoDB runtime, not H2 or another engine. No general database performance claim follows.

## Artifacts and reproducibility

Baseline source is `9be2868` (runtime source from the checkpoint-capacity fix). The final implementation is `1eac5a0`. Measurement metadata records the checkout's base commit because runs preceded the implementation commit; the corrected artifact hash identifies the subsequently committed runtime. Original unrelated user whitespace edits were left outside the commit.

Both runs generated byte-identical WAL fixtures:

- 4,000 rows: `39db45fa743572188811fa814fd61d6171bc8bf2b184276af47c35c18f8bbddd`.
- 16,000 rows: `ea1dd2e54a059e35f228de05c6d33a9b685d89f4a9aa9f498f3bfc4b512e81bc`.

The probe intentionally uses internal codec types for fixture construction and is tied to these source revisions. With JDK 17, compile it against a classpath containing the runtime and Kotlin stdlib, then run against each runtime in a separate empty output directory:

```sh
javac -cp "$KOKO_CLASSPATH" RecoveryProbe.java
for fork in 1 2 3; do
  java -Xms64m -Xmx256m -XX:-UsePerfData -cp ".:$KOKO_CLASSPATH" RecoveryProbe "/tmp/recovery-$fork"
done
```

Exact commands, platform, source hash, JAR hash and per-process RSS are in `before/environment.json` and `after/environment.json`. No builds or other qualification workloads ran during measurement. The local record also retains initial experiments, the intermediate implementation's observations and all generated database files.

## Correctness and costs

- 5,000 seeded mixed splices agree with the former immutable replay algorithm, retained only as a test reference. Cases include middle insertion/deletion, changed primary keys, swaps, keyless duplicate rows and multiple tables.
- Additional tests reject predecessor/schema/creation mismatches, collisions with retained keys, and reuse of a failed or completed builder. A late valid-checksum collision in the second table fails open without altering snapshot or WAL bytes.
- The final full build passes 145 tests, including 95 injected I/O failures and existing process-crash/migration tests. Sample, storage/model smokes and compiler-consumer checks pass.
- A new run of the larger H2/reference-model qualification passes 17,244 statement attempts and 209,950 query comparisons, including 183 reopens and 93 checkpoints across memory/file modes and three seeds. Raw metadata and results are included under `differential/`; elapsed qualification times are not performance measurements.
- Mutable replay lists/key sets add temporary retained working state and are discarded after freezing. Equal-length replacements update positions directly; length-changing middle splices can still shift O(N) references. Hash-set collision behavior is not a worst-case constant-time guarantee.
- The runtime grows by 6,115 bytes, with no new runtime dependency. Live INSERT uniqueness checks, WAL diff detection, physical power-loss qualification and JVM heap bounds remain separate concerns.
